# إزالة الوحدات الأساسية — الإصدار V7

أزيل جدول base_units وحقول الربط القديمة من units وبنود المستندات. أزيلت قائمته ومساره من الواجهة وAPI. شاشة الوحدات تطلب الاسم والاختصار فقط، والمنتج يختار وحدة واحدة للمخزون والبيع والشراء. لا يوجد تحويل كرتونة/قطعة؛ تبقى الكميات بنسبة 1:1 كما في النسخة السابقة.

## ترقية نسختك الحالية

الحزمة الكاملة تتضمن تحديث الفواتير والإصلاحات السابقة. احتفظ بأي تعديلات محلية أجريتها على ملفات المصدر قبل فكها.

```bash
unzip -o ~/Downloads/mpos-units-unified.zip -d ~/Storage/mpos-testing
cd ~/Storage/mpos-testing/mpos-architecture
bash scripts/upgrade-units.sh
```

السكربت يبني الصور أولًا، ويوقف الواجهة وAPI مؤقتًا، ويأخذ نسخة PostgreSQL احتياطية بصيغة custom داخل backups ثم يفحص فهرسها. لا يبدأ الترحيل إذا فشلت النسخة؛ يعيد تشغيل الحاويات الموجودة. بعد نجاح النسخة يشغّل الإصدار الجديد ويجري الفحص. لا تحذف backups، ولا تستخدم down -v، ولا تعِد تحميل البيانات التجريبية للترقية. لا تدعم الترقية تشغيل نسخة API قديمة وجديدة معًا على القاعدة نفسها.

إذا فشلت الترقية لا تشغّل إصدارًا قديمًا عشوائيًا على قاعدة قد تكون رُقّيت. احتفظ بالنسخة الاحتياطية وراجع سجلات api. استعادة القاعدة يجب أن تكون مع ملفات وصور الإصدار الموافق لها؛ لا ينفذ السكربت استعادة تلقائية قد تمحو عمليات لاحقة.

بعد النجاح اضغط Ctrl+Shift+R. القائمة الوحيدة للوحدات هي /#/app/units. أنشئ وحدة ثم اخترها في إنشاء/تعديل المنتج. يُمنع تغيير وحدة المنتج بعد وجود حركات مخزون، ويُمنع حذف وحدة مستخدمة. قد تحتاج إعادة فتح مسودة كانت مفتوحة قبل التحديث.

للتثبيت الجديد فقط: bash scripts/start.sh، ثم python3 scripts/seed-demo.py إذا أردت البيانات الاسترشادية. لا تحتاج سكربت الترقية إذا لم توجد قاعدة سابقة.

## كيف حُفظت البيانات؟

- يحتفظ الترحيل بكل الوحدات الموجودة ومعرّفاتها.
- لكل وحدة أساسية قديمة: يعاد استخدام وحدة تابعة لها بالاسم نفسه إن وجدت؛ وإلا تنشأ وحدة عادية باسمها. عند تعارض الاسم مع وحدة أخرى يضاف لاحقة migrated ومعرّف لمنع الدمج الخاطئ. ينطبق ذلك أيضًا على الوحدات الأساسية غير المستخدمة حتى لا تضيع أسماؤها.
- تنتقل وحدة مخزون المنتج إلى الوحدة المقابلة، وتصبح وحدتا البيع والشراء الافتراضيتان مطابقتين لها. هذا يغيّر الاختيار الافتراضي للمنتج إذا كانت أسماؤه السابقة مختلفة، لكنه لا يغيّر السعر أو الكمية لأن النموذج القديم كان 1:1.
- تبقى معرّفات وحدات بنود الفواتير القديمة كما هي، وتُنقل وحدة المخزون المرجعية إلى units. يُحفظ اسم الوحدة نصيًا للطباعة، بما فيها البنود التي لم تحدد وحدة بيع/شراء سابقًا.
- تستمر المسودات القديمة في الترحيل/الإلغاء طالما وحدة مخزون المنتج لم تتغير. عند تعديل المسودة تُستخدم وحدة المنتج الحالية صراحةً.
- لا تتغير الكميات أو الأرصدة أو حركات المخزون أو رؤوس المستندات أو الدفعات. تتم خطوات Flyway في معاملة واحدة.
- حقول product_unit وsale_unit وpurchase_unit ما زالت في API للتوافق مع باقي الشاشات، لكن جميعها تشير إلى units وتكون متساوية في المنتجات الجديدة والمُرحّلة. المورد /api/base-units أزيل؛ استخدم /api/units بدلًا منه. العملاء الخارجيون يجب أن يعيدوا تحميل معرّفات المنتجات/الوحدات بعد الترقية، ولا يفترضوا أن معرّف الوحدة الأساسية القديم هو معرّف الوحدة الجديدة.

## قبول التحديث

راجع مخزون منتج وفاتورة سابقة قبل وبعد التحديث. افتح الفاتورة وتأكد من اسم الوحدة، ثم أنشئ وحدة جديدة ومنتجًا بها وجرّب شراء/بيع وطباعته. احتفظ بالنسخة الاحتياطية حتى تنتهي من القبول.

- اختبار ترحيل قاعدة V6 إلى V7 تحقق من بقاء الأرصدة والحركات والدفعات والإجماليات ومن حفظ أسماء وحدات الفواتير.
- فُحص تركيب سكربت الترقية؛ تشغيل Docker والنسخ الاحتياطي والطباعة الفعلية على جهازك تحتاج تحققًا بعد التثبيت.
- الحزمة تشمل مصدر التطبيق القابل للتشغيل كاملًا؛ لا تشمل مجلد Laravel المرجعي القديم.
