# معمارية MPOS

## القرار

Modular Monolith: خلفية Spring واحدة وقاعدة PostgreSQL واحدة، مع واجهة React مستقلة. التقسيم حسب وحدات البزنس أولًا، ثم طبقات داخل الوحدة. لا حاجة حاليًا إلى Microservices أو Kafka أو Redis؛ لا تُضاف إلا إذا ظهرت حاجة تشغيلية قابلة للقياس.

## الوحدات الموجودة فعليًا

| الوحدة | النطاق |
| --- | --- |
| `identity` | تسجيل الدخول والمستخدمون والأدوار والصلاحيات |
| `catalog` | المنتجات والتصنيفات والعلامات والوحدات وبيانات الأطراف الحالية |
| `warehouses` | تعريف المخازن |
| `purchasing` | مسودات المشتريات والحسابات والاستلام والإلغاء |
| `inventory` | الأرصدة والافتتاحيات والتسويات والتحويلات وسجل الحركة |
| `media` | التحقق من الصور وتخزينها واسترجاعها |
| `settings` | إعدادات الشركة واللغة وبيانات تهيئة الواجهة |
| `shared` | أخطاء البزنس والتحقق والبنية المشتركة لمنع تكرار الطلبات |

المبيعات والمدفوعات والتقارير وحدات لاحقة؛ لا توجد مجلدات فارغة توحي بأنها منفذة. العملاء والموردون ما زالا ضمن الكتالوج؛ فصل `partners` مؤجل إلى ظهور حالات استخدام مستقلة.

## الطبقات والمسؤوليات

- `api`: Controller يحوّل HTTP إلى استدعاء خدمة ويعيد الاستجابة؛ لا SQL ولا معاملات قاعدة بيانات. ترجمة multipart وResponseEntity هنا فقط.
- `application`: تنظيم حالات الاستخدام والصلاحيات والمعاملات. الحدود المستخدمة بين الوحدات هنا، مثل `StockOperations`.
- `domain`: حسابات وقواعد مستقلة عن Spring وHTTP وJDBC، مثل `PurchaseMath` و`StockPolicy` وأخطاء البزنس.
- `infrastructure`: تنفيذ منافذ التخزين والتكامل، مثل `JdbcPurchaseRepository` و`JdbcStockRepository` و`JdbcInventoryQueries` وتنفيذ منع التكرار.

المشتريات تعتمد على `StockOperations`، ولا تكتب جداول المخزون مباشرة. خدمات المشتريات والمخزون تعتمد على منافذ تخزين، ويحقن Spring تطبيق JDBC. لا توجد واجهة صورية لكل كلاس؛ الواجهات عند حدود التخزين أو التعامل بين الوحدات.

React هو الـ View في هذا التصميم. Spring يوفر REST Controllers؛ لا توجد حاجة إلى صفحات JSP أو Thymeleaf. نماذج البزنس والقواعد في الخلفية هي المرجع، ولا تعتمد صحة الحسابات على JavaScript.

## المعاملات والتزامن

استلام الشراء أو إلغاؤه وتغيير المخزون ومفتاح منع التكرار تشارك معاملة واحدة. `StockService` وتنفيذ منع التكرار يشترطان معاملة موجودة باستخدام `Propagation.MANDATORY` لمنع استدعائهما خطأ خارج سياق ذري. تُقفل أرصدة المخازن والمنتجات بترتيب ثابت، وتُحفظ أقفال وثائق الشراء وفحوص version. بقيت قيم الأموال BigDecimal وترحيلات Flyway كما هي.

## الفرونت إند

`frontend/src/features/purchasing` و`inventory` و`settings` تحتوي الشاشات الحديثة. `src/app` يحتوي مكونات تهيئة وعرض التطبيق الجديدة، و`src/shared` للمكونات المشتركة. شاشات React القديمة وRedux ما زالت في مواقعها الداخلية المتوافقة؛ إعادة تقسيمها بالكامل حسب الميزات تتم تدريجيًا لتجنب كسر المسارات المعطّلة حتى الآن. ملفات npm والبناء مستقلة عن Laravel، وإن كان البناء لا يزال يستخدم Laravel Mix كأداة webpack دون تشغيل PHP.

## حدود المرحلة الحالية بصراحة

هذه إعادة هيكلة فعلية وليست اكتمالًا لكل تحسينات SOLID:

- كل Controllers أصبحت دون SQL أو معاملات. خدمات التطبيق لا تستقبل طلبات Servlet أو MultipartFile ولا تعيد ResponseEntity.
- الفصل الكامل بين قواعد العمل والتخزين منفذ للمشتريات والمخزون. خدمات الكتالوج والهوية والإعدادات والمخازن والوسائط ما زالت تحتوي JDBC، وتحتاج استخراج Repositories متخصصة لاحقًا؛ لم نخفِ SQL وراء واجهات عامة شكلية.
- بعض طلبات واستجابات API القديمة ما زالت Map للحفاظ على تعاقد React الحالي. توجد Records عند حدود محددة، لكن تحويل جميع العقود إلى DTOs مسماة لم ينتهِ.
- `legacy/laravel` مرجع تاريخي، وليس حزمة تشغيل Laravel مكتملة بعد نقل موارد React المشتركة.

## اختبارات الحماية

اختبارات التكامل الحالية تغطي الدخول والصلاحيات والكتالوج والمشتريات والتزامن وعدم سلبية المخزون ومنع التكرار. أضيفت اختبارات قواعد المخزون واختبارات معمارية تمنع دخول Spring إلى domain أو SQL والمعاملات إلى Controllers أو تفاصيل JDBC إلى طبقات تطبيق المشتريات والمخزون. هذه فحوص حدود بالمصدر وليست إثباتًا آليًا لكل مبادئ SOLID.

## التوسع التالي

استخراج Repositories للوحدات المتبقية وتوحيد DTOs، ثم بناء `sales` باستخدام حد المخزون الموجود، ثم `payments` و`returns` و`reporting`. تقييم Microservices يأتي عند وجود ضرورة فعلية لفصل النشر أو فرق مستقلة، وليس لمجرد زيادة عدد الملفات.
