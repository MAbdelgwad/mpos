# معمارية MPOS

## القرار

Modular Monolith: خلفية Spring واحدة وقاعدة PostgreSQL واحدة، مع واجهة React مستقلة. التقسيم حسب وحدات البزنس أولًا، ثم طبقات داخل الوحدة. لا حاجة حاليًا إلى Microservices أو Kafka أو Redis؛ لا تُضاف إلا إذا ظهرت حاجة تشغيلية قابلة للقياس.

## الوحدات الموجودة فعليًا

| الوحدة | النطاق |
| --- | --- |
| `identity` | تسجيل الدخول والمستخدمون والأدوار والصلاحيات |
| `catalog` | المنتجات والتصنيفات والعلامات والوحدات وبيانات الأطراف الحالية |
| `warehouses` | تعريف المخازن |
| `purchasing` | مسودات المشتريات والحسابات والاستلام والإلغاء |
| `payments` | دفعات العملاء والموردين وعكسها ورصيد الفاتورة |
| `sales` | مسودات المبيعات والحسابات والإتمام والإلغاء |
| `inventory` | الأرصدة والافتتاحيات والتسويات والتحويلات وسجل الحركة |
| `media` | التحقق من الصور وتخزينها واسترجاعها |
| `settings` | إعدادات الشركة واللغة وبيانات تهيئة الواجهة |
| `shared` | أخطاء البزنس والتحقق والبنية المشتركة لمنع تكرار الطلبات |

المرتجعات والتقارير وحدات لاحقة؛ لا توجد مجلدات فارغة توحي بأنها منفذة. العملاء والموردون ما زالا ضمن الكتالوج؛ فصل `partners` مؤجل إلى ظهور حالات استخدام مستقلة.

## الطبقات والمسؤوليات

- `api`: Controller يحوّل HTTP إلى استدعاء خدمة ويعيد الاستجابة؛ لا SQL ولا معاملات قاعدة بيانات. ترجمة multipart وResponseEntity هنا فقط.
- `application`: تنظيم حالات الاستخدام والصلاحيات والمعاملات. الحدود المستخدمة بين الوحدات هنا، مثل `StockOperations`.
- `domain`: حسابات وقواعد مستقلة عن Spring وHTTP وJDBC، مثل `InvoiceMath` و`SaleMath` و`PurchaseMath` و`StockPolicy` وأخطاء البزنس.
- `infrastructure`: تنفيذ منافذ التخزين والتكامل، مثل `JdbcPurchaseRepository` و`JdbcStockRepository` و`JdbcInventoryQueries`، ومستودعات الهوية والكتالوج والإعدادات والمخازن والصور، وتنفيذ منع التكرار.

المشتريات والمبيعات تعتمدان على `StockOperations`، ولا تكتبان جداول المخزون مباشرة. كل خدمات التطبيق الحالية تعتمد على منافذ تخزين، ويحقن Spring تطبيق JDBC. خدمة الكتالوج تعتمد أيضًا على واجهة BarcodeRenderer، ولا تعتمد على تطبيق مكتبة الباركود مباشرة. لا توجد واجهة صورية لكل كلاس؛ الواجهات عند حدود التخزين أو التعامل بين الوحدات.

React هو الـ View في هذا التصميم. Spring يوفر REST Controllers؛ لا توجد حاجة إلى صفحات JSP أو Thymeleaf. نماذج البزنس والقواعد في الخلفية هي المرجع، ولا تعتمد صحة الحسابات على JavaScript.

## المعاملات والتزامن

استلام الشراء أو إلغاؤه وتغيير المخزون ومفتاح منع التكرار تشارك معاملة واحدة. `StockService` وتنفيذ منع التكرار يشترطان معاملة موجودة باستخدام `Propagation.MANDATORY` لمنع استدعائهما خطأ خارج سياق ذري. تُقفل أرصدة المخازن والمنتجات بترتيب ثابت، وتُحفظ أقفال وثائق الشراء وفحوص version. بقيت قيم الأموال BigDecimal وترحيلات Flyway كما هي.

## الفرونت إند

`frontend/src/features/purchasing` و`sales` و`inventory` و`settings` تحتوي الشاشات الحديثة. `src/app` يحتوي مكونات تهيئة وعرض التطبيق الجديدة، و`src/shared` للمكونات المشتركة. شاشات React القديمة وRedux ما زالت في مواقعها الداخلية المتوافقة؛ إعادة تقسيمها بالكامل حسب الميزات تتم تدريجيًا لتجنب كسر المسارات المعطّلة حتى الآن. ملفات npm والبناء مستقلة عن Laravel، وإن كان البناء لا يزال يستخدم Laravel Mix كأداة webpack دون تشغيل PHP.

## حدود المرحلة الحالية بصراحة

هذه إعادة هيكلة فعلية وليست اكتمالًا لكل تحسينات SOLID:

- كل Controllers أصبحت دون SQL أو معاملات. خدمات التطبيق لا تستقبل طلبات Servlet أو MultipartFile ولا تعيد ResponseEntity.
- اكتمل استخراج JDBC وSQL من جميع طبقات application إلى Repositories متخصصة لكل وحدة. واجهات المستودعات تحتوي عمليات مسماة، ولا تعرض تنفيذ SQL عام للخدمات. جداول وحقول الكتالوج المسموح بها محددة في CatalogSchema، ويتحقق تطبيق JDBC منها قبل بناء الاستعلامات.
- عقود الدخول واستجابته، وتغيير كلمة المرور، واللغة، والمخازن، ومحتوى الصور أصبحت DTOs/Records واضحة. بعض عقود الكتالوج والمشتريات وإدارة المستخدمين والأدوار ما زالت Map للتوافق مع React؛ تحويلها كلها لم ينتهِ. أصبحت تواريخ رؤوس المشتريات LocalDate، ويحدث تحويل JDBC داخل المستودع.
- `legacy/laravel` مرجع تاريخي، وليس حزمة تشغيل Laravel مكتملة بعد نقل موارد React المشتركة.

## اختبارات الحماية

اختبارات التكامل الحالية تغطي الدخول والصلاحيات والكتالوج والمشتريات والمبيعات والتزامن وعدم سلبية المخزون ومنع التكرار. أضيفت اختبارات قواعد المخزون واختبارات معمارية تمنع دخول Spring إلى domain أو SQL والمعاملات إلى Controllers أو تفاصيل JDBC وSQL أو تطبيقات infrastructure إلى جميع طبقات application. هذه فحوص حدود بالمصدر وليست إثباتًا آليًا لكل مبادئ SOLID.

## التوسع التالي

استكمال DTOs لعقود الكتالوج والمشتريات وإدارة المستخدمين والأدوار، ثم بناء `returns` و`reporting` واستكمال POS. تقييم Microservices يأتي عند وجود ضرورة فعلية لفصل النشر أو فرق مستقلة، وليس لمجرد زيادة عدد الملفات.

## تحقق إصدار المستودعات

نجح Maven verify: 31 اختبارًا منفذًا، واختبار متصفح اختياري واحد متجاوز (32 إجمالًا). تشمل الإضافات اختبار تغيير كلمة المرور وإبطال جميع جلسات المستخدم، وعدم تسريب حقول الاعتماد في استجابة الدخول، وحفظ اللغة، والتراجع الذري عن إعدادات غير صالحة، وتقييد إحصاءات الوحدات حسب الصلاحيات. الواجهة لم تتغير في هذا الإصدار. تشغيل Docker والمتصفح ما زال غير متحقق في بيئة الإعداد.

## تحديث المبيعات

وحدة sales تستخدم SaleRequest بعقد إدخال واضح، وSaleRepository منفصلًا للتخزين، وStockOperations لترحيل المخزون في المعاملة نفسها. InvoiceMath يجمع حسابات الخصومات والضرائب المشتركة دون اعتماد على Spring. استجابات المبيعات لا تزال Map للتوافق مع الواجهة؛ تحويل كل العقود إلى DTOs ليس مكتملًا.

التحقق الحالي: 41 اختبارًا ناجحًا واختبار متصفح اختياري متجاوز. تشمل الإضافات دورة البيع والإلغاء، البيع المتزامن فوق الرصيد، إعادة الطلب نفسه، ترابط إلغاء الشراء مع المخزون المباع، التراجع متعدد الأصناف، الصلاحيات، وترقية قاعدة V3 إلى V4 مع الحفاظ على سجل مخزن موجود. لا تعني هذه الاختبارات اكتمال القبول التفاعلي أو المحاسبي.

## تحديث المدفوعات

PaymentService ينسق الصلاحيات والمعاملات ومنع التكرار عبر PaymentRepository. وحدتا البيع والشراء تعتمدان على منفذ PaymentBalances لحساب المدفوع والتحقق قبل الإلغاء، دون استدعاء تفاصيل JDBC. قفل رأس المستند يسبق إدخال الدفعة أو عكسها، وهو القفل نفسه في إلغاء المستند، لمنع التداخل مع الدفع. لا تنشئ الدفعات حركات مخزون. Settlement يحتفظ بحساب المتبقي مستقلًا عن Spring.

PaymentRequest وVoidRequest يحددان مدخلات HTTP؛ بيانات JDBC الخاصة بالتواريخ تتحول إلى تاريخ محلي أو Instant داخل المستودع. مكون PaymentPanel مشترك بين شاشة المشتريات والمبيعات. V5 ترحيل إضافي، والنسخ السابقة من Flyway محفوظة.

تحقق حزمة المدفوعات: 47 اختبارًا ناجحًا، واختبار متصفح اختياري متجاوز. نجح بناء React مع تحذيري CSS سابقين؛ Docker والمتصفح يحتاجان اختبارًا محليًا.
