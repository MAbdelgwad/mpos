# تسجيل تحصيل العملاء وسداد الموردين

تتيح هذه المرحلة تسجيل دفعات منفذة خارج التطبيق على فاتورة بيع مكتملة أو شراء مستلمة. يدعم النظام النقدي CASH والبنك BANK والبطاقة CARD كبيانات وصفية؛ لا ينفذ تحويلًا ماليًا أو اتصالًا ببوابة دفع. المبلغ والتاريخ والطريقة والمرجع والملاحظات تحفظ مع المستخدم ووقت التسجيل.

## القواعد

- المبلغ موجب وبدقة حتى أربع منازل، ولا يتجاوز المتبقي على الفاتورة. الصفر والسالب والدقة الزائدة مرفوضة.
- يسمح بدفعات جزئية أو كاملة. paid_amount مجموع الدفعات غير المعكوسة؛ due_amount الإجمالي ناقص هذا المجموع. payment_status: 1 مسدد/لا متبقي، 2 غير مسدد، 3 جزئي. المستند الملغى متبقيه صفر وليس ذلك إثبات تحصيل.
- لا دفعات على مسودة أو مستند ملغى. لا حجز مخزون أو حركة مخزون نتيجة الدفع نفسه.
- يستخدم إنشاء الدفعة Idempotency-Key. إعادة الطلب بالمفتاح والجسم نفسيهما لا تسجل دفعة ثانية؛ تغيير الجسم بالمفتاح نفسه يرفض بـ409.
- لا يسمح بإلغاء فاتورة لها دفعات سارية. اعكس تسجيل الدفعات أولًا ثم ألغِ المستند؛ معالجة النقود/ردها تتم خارج هذا التطبيق.
- عكس الدفعة يحتاج سببًا. يحتفظ النظام بالمبلغ الأصلي والمستخدم والتاريخ، ويسجل منفذ العكس ووقته وسببه. لا يوجد حذف أو تعديل مباشر. إعادة طلب العكس لا تغيّر التدقيق الأصلي.
- قفل رأس الفاتورة يسلسل الدفع والعكس والإلغاء. طلبان متزامنان لا يستطيعان سداد أكثر من المستحق. أي فشل يرجع المعاملة ومفتاح الطلب معًا.
- الرد المحفوظ لطلب إنشاء مكرر يعكس نتيجة الإنشاء الأصلية؛ استعلم عن القائمة لقراءة أحدث حالة، خاصة إذا عُكست الدفعة لاحقًا.

## الواجهة والصلاحيات

من المبيعات أو المشتريات اضغط عرض، ثم استخدم قسم التحصيل/السداد. يظهر للمستخدم صاحب manage_payments مع صلاحية إدارة المستند. يضيف V5 الصلاحية إلى ADMIN تلقائيًا. الأدوار المخصصة تحتاج منحها يدويًا من إدارة الأدوار. تستمر صلاحيات المنتجات والمخازن والعملاء/الموردين في التحكم بقوائم إنشاء الفواتير.

## API

استبدل type بـsales أو purchases وid بمعرّف الفاتورة. كل الطلبات تحتاج Authorization: Bearer.

| الطلب | الاستخدام |
| --- | --- |
| GET /api/{type}/{id}/payments | سجل الدفعات مع summary.paid وsummary.due وsummary.status |
| POST /api/{type}/{id}/payments | تسجيل دفعة؛ Idempotency-Key إلزامي |
| POST /api/{type}/{id}/payments/{paymentId}/void | عكس دفعة لهذا المستند فقط |

جسم التسجيل:

```json
{"amount":40,"date":"2026-11-14","method":"CASH","reference":"Receipt 001","notes":"دفعة أولى"}
```

جسم العكس:

```json
{"reason":"إدخال مكرر تمت تسويته خارج التطبيق"}
```

تُحفظ التواريخ كتاريخ محلي YYYY-MM-DD، وتواريخ التدقيق كوقت UTC. يعاد 422 لمدخلات غير صالحة، و409 لتجاوز المتبقي أو حالة مستند غير مناسبة، و403 لغياب الصلاحيات، و404 لدفعة ليست مرتبطة بالمستند المحدد.

## اختبار قبول يدوي

1. أنشئ بيعًا مكتملًا إجماليه 100 بدون ضرائب/خصومات، مع رصيد مخزون كافٍ.
2. افتح عرض الفاتورة وسجّل 40: المدفوع 40 والمتبقي 60.
3. حاول تسجيل 61: يجب الرفض دون إضافة دفعة. سجّل 60: المتبقي صفر.
4. حاول إلغاء الفاتورة: يرفض لوجود دفعات سارية.
5. اعكس دفعة 40 بسبب واضح: المتبقي يعود 40، ويبقى السجل المعكوس ظاهرًا.
6. اعكس الدفعة الأخرى ثم ألغِ الفاتورة: تعود الكميات إلى المخزون، والمتبقي صفر.
7. كرر السيناريو على شراء مستلم، وتحقق أن السداد لا يغير كمية المخزون.
8. اختبر مستخدمًا لا يملك manage_payments؛ قسم الدفعات مخفي والـAPI يرفض الوصول.

اختبارات التكامل تغطي السداد الجزئي والكامل والعكس، التكرار والتزامن وتجاوز المستحق، تداخل الدفع مع الإلغاء، التحقق والصلاحيات، وعدم عكس دفعة لمستند مختلف، والترقية من V4 مع الحفاظ على فاتورة موجودة.

## خارج نطاق هذه المرحلة

المرتجعات الجزئية، الرد المالي الآلي، POS، السلف والمحافظ، توزيع دفعة واحدة على عدة فواتير، كشف حساب مجمع للعميل/المورد، الحسابات البنكية والصندوق والتسويات، القيود المحاسبية، العملات المتعددة، إيصال PDF، والتكامل مع بوابات الدفع. تشغيل Docker وتجربة المتصفح لهذا الإصدار لم يتحققا في بيئة الإعداد؛ اختبرهما محليًا قبل اعتماد أي دورة عمل.
