# المشتريات والمخزون — الدفعة الثالثة

هذه الدفعة تضيف المشتريات والأرصدة الافتتاحية والتسويات والتحويلات وسجل الحركة. المبيعات والمدفوعات والمرتجعات والتقييم المحاسبي للمخزون لم تُنفذ بعد.

## التشغيل

اتبع `backend/README.md`. بعد جلب الفرع المحدث أعد البناء من مجلد `backend`:

```bash
docker compose up --build -d
```

افتح `http://localhost:8081`. الحساب الإداري يحصل على الصلاحيات الجديدة من ترحيل V3. تظهر «المشتريات» و«المخزون» في الشريط العلوي. V1 وV2 لم يتغيرا، ولا يلزم حذف قاعدة البيانات.

## دورة المشتريات

| الحالة | أثرها على المخزون | المسموح |
| --- | --- | --- |
| معلق، 2 | لا زيادة | تعديل أو استلام أو إلغاء |
| مطلوب، 3 | لا زيادة | تعديل أو استلام أو إلغاء |
| مستلم، 1 | إضافة الكميات للمخزن | عرض أو إلغاء؛ المستند مقفل للتعديل |
| ملغى، 4 | عكس الاستلام إن وجد | عرض فقط |

إنشاء مستند بحالة «مستلم» يسجل الاستلام فورًا. المستند المعلق/المطلوب يُستلم بزر الاستلام. الإلغاء يحتفظ بالمستند وسجل الأصناف ويسجل حركة عكسية؛ إذا استُهلكت الكمية ولم يعد الرصيد يكفي، يُرفض الإلغاء بالكامل. تكرار استلام/إلغاء المستند لا يسجل حركة ثانية. تعديل المسودة يتطلب `version` الحالية لمنع الكتابة فوق تعديل أحدث.

هذه نقطة اختلاف مقصودة عن التنفيذ القديم الذي يضيف المخزون عند الحفظ دون فحص حالة الاستلام. أُبقيت رموز الحالات الأصلية 1/2/3، وأضيفت 4 للإلغاء بدل الحذف الفعلي.

## قواعد الحساب

- كل كمية موجبة، والتكلفة والخصومات والشحن غير سالبة.
- نوع الخصم 1 نسبة من تكلفة الوحدة؛ 2 مبلغ لكل وحدة. خصم الوحدة لا يتجاوز تكلفتها، والنسبة لا تتجاوز 100%.
- نوع الضريبة 1 مضافة بعد الخصم؛ 2 مشمولة في السعر بعد الخصم.
- تُجمع إجماليات الأصناف، ثم يُطرح خصم الفاتورة، ثم تُضاف ضريبة الفاتورة والشحن.
- حافظ التنفيذ على قيد المصدر: الشحن لا يتجاوز الإجمالي قبل الشحن.
- الحساب بـBigDecimal، وتقريب المبالغ على مستوى الصنف إلى أربع منازل بـHALF_UP. يُعرض صافي تكلفة الوحدة بثماني منازل؛ لا يُعاد حساب ضريبة السطر من قيمة عرض مقربة.
- يتجاهل الخادم الإجماليات المرسلة مثل grand_total وtax_amount ويحسبها بنفسه. زر «حساب الإجمالي» يعرض النتيجة من الخادم قبل الحفظ.
- لا تسجل هذه الدفعة سداد المورد؛ paid_amount وreceived_amount غير الصفريين مرفوضان صراحةً.

مثال مرجعي: تكلفة 115، كمية 2، خصم ثابت 5 لكل وحدة، ضريبة مضافة 10% → إجمالي الأصناف 242. خصم فاتورة 12 وضريبة فاتورة 15% وشحن 10 → الإجمالي 274.5000.

## وحدات القياس

يتبع النظام حاليًا نموذج المصدر دون معامل تحويل بين الوحدات: الكميات تُدخل بوحدة المنتج الأساسية بنسبة 1:1. لا توجد معالجة آلية لكرتونة تحتوي عدة قطع. تُحفظ الوحدة الأساسية مع بند الشراء، ويُرفض استلام مسودة إذا تغير معنى وحدة المنتج حتى تُراجع المسودة وتُحفظ. بعد وجود حركة مخزون لا يمكن تغيير الوحدة الأساسية للمنتج.

## حركات المخزون

- الرصيد الافتتاحي: كمية موجبة، متاح مرة واحدة لكل منتج/مخزن قبل أي حركة عليه.
- التسوية: كمية موجبة للإضافة أو سالبة للخصم، مع سبب إلزامي.
- التحويل: خصم وإضافة بالمقدار نفسه بين مخزنين مختلفين، داخل معاملة واحدة؛ لا توجد مرحلة «في الطريق» في هذه الدفعة.
- لا يسمح بأي رصيد سالب. تُقفل صفوف الأرصدة بترتيب ثابت أثناء العملية لمنع تضارب الطلبات المتزامنة.
- سجل الحركات يحفظ المنتج والمخزن والتغير والرصيد بعد الحركة والسبب والمنفذ ومرجع الشراء عند وجوده. لا توجد API لتعديل السجل أو حذفه.
- الأرصدة المعروضة في كتالوج المنتجات أصبحت فعلية ومجمعة عبر المخازن.

## واجهات API

| المسار | الاستخدام |
| --- | --- |
| `GET /api/purchases` | قائمة مرقمة، بحث وفلتر status |
| `POST /api/purchases` | إنشاء شراء؛ يتطلب Idempotency-Key |
| `POST /api/purchases/preview` | حساب إجمالي دون حفظ |
| `GET /api/purchases/{id}` | المستند والأصناف |
| `PUT /api/purchases/{id}` | تعديل مسودة مع version |
| `POST /api/purchases/{id}/receive` | استلام |
| `POST /api/purchases/{id}/cancel` | إلغاء وعكس المخزون إن لزم |
| `GET /api/inventory/balances` | الأرصدة؛ فلاتر warehouse_id وproduct_id |
| `GET /api/inventory/movements` | سجل الحركات بنفس الفلاتر |
| `POST /api/inventory/opening` | product_id، warehouse_id، quantity، reason |
| `POST /api/inventory/adjustments` | product_id، warehouse_id، quantity_delta، reason |
| `POST /api/inventory/transfers` | product_id، from_warehouse_id، to_warehouse_id، quantity، reason |

العمليات الثلاث الأخيرة تتطلب أيضًا Idempotency-Key: من 8 إلى 128 حرفًا من الأحرف والأرقام وشرطة/شرطة سفلية. إعادة نفس المفتاح ونفس البيانات للمستخدم نفسه تعيد نتيجة الطلب الأصلية بلا حركة إضافية. استخدامه مع بيانات مختلفة يعطي 409. فشل العملية يعيد كل التغييرات بما فيها حجز المفتاح. عند انقطاع الشبكة أعد إرسال الطلب نفسه؛ راجع السجل قبل البدء بطلب جديد.

الصلاحيات: manage_purchase، manage_inventory، manage_adjustments، manage_transfers. شاشات الاختيار تحتاج أيضًا صلاحيات قراءة/إدارة المنتجات والمخازن والموردين وفق نموذج الصلاحيات الحالي. الدور VIEWER لا يستطيع تعديل المخزون أو إنشاء المشتريات.

## تجربة يدوية مقترحة

1. أنشئ منتجًا وموردًا ومخزنين؛ استخدم نفس الوحدة الأساسية للمنتج ووحدتي البيع والشراء.
2. سجل رصيدًا افتتاحيًا 10 في المخزن الأول. يجب أن يصبح الرصيد 10.
3. حول 3 للمخزن الثاني: يجب أن تظهر الأرصدة 7 و3.
4. حاول تحويل 8 من الأول: تُرفض العملية وتظل الأرصدة 7 و3.
5. أنشئ شراء معلقًا بكمية 2: لا تتغير الأرصدة. استلمه في الأول: يصبح 9.
6. ألغِ الشراء: يعود الأول إلى 7 وتبقى حركة الاستلام وحركة عكسها ظاهرتين.
7. اختبر عرض الصنف وسجل الحركات وتحديث الصفحة للتأكد من استمرار الأرصدة.

اختبارات PostgreSQL تشمل الحسابات، والتزامن، ومنع السالب، وإعادة الإرسال، والتراجع الذري، وإلغاء شراء استُهلك جزء منه، وتغير وحدة مسودة قبل الاستلام. بناء React اجتاز الترجمة؛ اختبار المتصفح الكامل وDocker ما زالا يحتاجان التشغيل محليًا بسبب قيود بيئة التنفيذ.
